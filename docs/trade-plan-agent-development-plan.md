## 1. 开发目标

下一阶段以“可持续跟踪的交易计划”为主线，不以增加工具数量为目标。

打通以下工作流：

```text
研究 → 保存计划 → 跨会话恢复 → 跟踪变化 → 风险预检 → 执行 → 证据复盘
```

典型用户场景：

1. 用户要求分析一个标的，保存观察计划，记录入场条件、失效条件和风险说明，暂时不交易。
2. 用户第二天重新打开 Ti，继续原计划，了解哪些条件发生变化。
3. 用户决定执行时，查看当前计划版本、订单预检和现有风控要求。
4. 执行后，用户能够对照当时的计划查看实际订单、成交、费用和偏差。

成功标准不是“模型记得聊天”，而是计划、观测、执行和复盘之间存在可靠关联。

目标用户先限定为：会交易、能使用 CLI、愿意自行决策、重视密钥自主控制的加密货币主动交易者。

## 2. 范围与授权边界

### 2.1 本轮必须完成

| 能力 | 第一版边界 |
| --- | --- |
| 交易计划与 Notebook | 结构化计划、版本记录、有来源的追加笔记 |
| 跨会话恢复 | 按账户作用域共享，不依赖 cwd 或旧对话摘要 |
| 条件跟踪 | 确定性求值、只读观测、失效与到期提醒 |
| 执行关联 | 计划版本与执行日志在提交前建立关联 |
| 证据复盘 | 对照当时计划与实际执行，明确证据缺口 |
| TUI 入口 | 计划列表、详情、操作、时间线和复盘 |
| 发布与试用 | 先完成现货模拟盘闭环，再决定限定范围实盘试点 |

### 2.2 本轮不新增

- 通用记忆平台、向量数据库和全量历史对话检索。
- 云同步、多设备协作、完整 Web 交易终端。
- 根据计划自动下单、多 agent 投票、自我修改策略或自动调参。
- 更多交易所、完整自研回测平台和全部合约能力。
- 独立的 24 小时托管守护服务。

“不新增”不代表删除现有功能。不得根据本文撤销其他 agent 正在开发或已经交付的能力。

保留现有直接交易路径及 `unattended` 配置语义。新增计划跟踪不扩大任何交易授权；计划关联实盘试点仍要求单独授权和逐单确认。

### 2.3 本文不授予的权限

本文不授权提交 Git commit、创建或发布 npm 版本、操作真实资金、调用付费模型、读取或外传凭证，也不授权向外部系统上传会话或账户数据。

实施必须遵守根目录 `AGENTS.md`。维护者另行决定任务分配、提交、发布、用户招募和实盘试点。

## 3. 核心设计决策

### 3.1 TradePlan 与 PreparedOrder 分开

`TradePlan` 是 Agent 层长期保存的交易想法与跟踪对象。

引擎已有的 `PreparedOrder` 是某个引擎实例生成的一次性执行对象，不能持久化后跨重启直接执行。每次交易仍须通过当前引擎重新准备和预检。

建议计划字段：

| 字段组 | 内容 |
| --- | --- |
| 身份 | 稳定 ID、计划版本、创建与更新时间 |
| 作用域 | 账户身份、paper/live、交易所、市场类型、报价币、持仓模式 |
| 研究对象 | 标的、周期、方向、简短交易依据 |
| 条件 | 观察条件、入场条件、失效条件、到期时间 |
| 风险说明 | 拟议数量、止损参考、风险估算及缺失数据 |
| 证据 | 来源、观测时间、证据引用 |
| 执行关联 | 提交意图 ID、执行记录 ID、所关联的计划版本 |
| 笔记 | 说明、作者类别、人或模型来源、时间 |

模型自由文本不得充当成交证据。账户、订单和持仓仍以交易引擎查询及执行日志为准。

### 3.2 三类状态不得混用

| 状态层 | 示例 | 决定者 |
| --- | --- | --- |
| 计划生命周期 | 草稿、跟踪中、已归档 | 用户操作；模型可提出草稿 |
| 条件评估 | 满足、不满足、未知、已到期 | 确定性求值与时间判断 |
| 执行状态 | 未提交、处理中、结果未知、已确认 | 执行日志和交易所观测 |

条件满足不等于批准交易。计划归档不等于撤单或平仓。单笔订单成交不等于整个计划结束。

现有仓位可能包含同标的其他计划或外部交易，不得仅凭持仓变化自动推断某个计划已经完成。

### 3.3 独立计划存储

建议存储位置：

```text
~/.ti-trader/agent/
  plans/
    <plan-id>.json
```

路径必须从现有 Ti 配置目录派生，支持 `TI_DATA_DIR`，不能硬编码用户主目录。模型只接受计划 ID，不接受真实文件路径。

每个计划文件保存版本和有界事件记录。列表索引可以重建，不作为权威状态；不得为了索引引入第二个无法一致提交的权威副本。

实现要求：

- 使用固定 schema、字段校验和格式版本。
- 使用现有文件锁、原子替换及同步落盘能力，文件权限保持私有。
- 文件名、内容 ID 和作用域须一致；不得接受路径穿越、外部路径或不受控符号链接目标。
- 修改采用预期版本校验，两个会话不得无提示互相覆盖。
- 内容版本与观测事件分开管理，后台追加观测不应伪装成用户修改了交易依据。
- 文件锁内只进行同步的读取、校验与写入；不得等待网络、模型或用户确认。
- 活跃计划数量等跨文件约束需要存储级锁保护，不能仅在内存中计数。
- 写入后才报告成功；写入失败、坏文件和未知格式必须显式报错。
- 崩溃遗留锁的处置应遵循现有风险状态的保守做法，不盲目按时间接管仍可能有写入者的锁。
- 超过容量限制明确报错，不静默删除历史。

建议初始产品限额：20 个活跃计划、单条正文 8 KiB、每轮索引 4 KiB，按 UTF-8 字节计算。D1 还须明确历史版本、事件和总文件体积上限，以及用户导出、清理的行为。

第一版不引入数据库依赖。不得将计划自由文本写入 `trading-state.json`。

### 3.4 作用域与 Paper 重置

复用 `TradingEngine.getExecutionScope()` 的作用域，不重新计算账户身份。

同一账户从不同 cwd 启动 Ti 应看到同一组计划。不同模式、账户、交易所和市场作用域不得隐式串用；用户可以查看旧计划，但不得把它自动迁移成当前账户的有效计划。

调研时 Paper 账户身份与存储路径有关，不能假定仅凭账户 ID 就能识别重置前后的模拟账户。D1 必须与运行时维护流程明确衔接：

- Paper 重置后保留旧计划。
- 暂停旧计划跟踪，并标记需要重新确认。
- 不把旧模拟账户的执行结果归入新模拟账户。
- 不把普通进程重启或无关配置更新误判为 Paper 重置。

### 3.5 权限

| 操作 | 规则 |
| --- | --- |
| 创建草稿、追加研究笔记 | 模型可执行 |
| 修改草稿 | 必须匹配预期版本 |
| 修改正在跟踪的入场、失效等条件 | 生成新版本草稿，用户确认后启用 |
| 启用跟踪、归档、删除 | 用户显式操作 |
| 写入观测事实和执行关联 | 程序通过可信接口生成 |
| 放宽风控、批准实盘订单 | 继续走现有用户授权与引擎规则 |

不开放通用 `read/write/bash`。Notebook 内容是非权威资料，不得提升为系统指令或用于修改工具权限。

计划故障不能成为新增的全局交易故障：明确拒绝依赖损坏计划的操作，但不额外阻断原有撤单、减仓和执行恢复路径。底层交易存储本身失败时仍遵循现有安全规则。

### 3.6 提交前关联，而不是成功后补关联

必须处理以下场景：交易所接受订单后，进程在往计划补写 `executionId` 前退出。

目标顺序：

```text
保存不可变计划版本与提交意图
→ 将引用随执行记录持久化
→ 现有风控、确认、提交和恢复
→ 从执行记录更新计划视图
```

引擎只接收有界的通用引用，不依赖完整 `TradePlan` 或读取笔记正文。引用不能混入交易所订单参数。

一个计划可能包含入场、保护、退出等多笔订单，因此每次提交意图需要独立 ID。相同提交意图的重复请求不能产生新的交易所提交；不得靠进程内对象身份实现跨重启去重。

当前执行日志的终态记录有数量上限，不能直接当永久复盘数据库。D5 必须确定归档契约，D6 完成消费和保留逻辑：在可靠归档前不得静默裁掉唯一关联证据，容量不足和归档失败必须可见。

不得用两次独立文件写入冒充原子事务。计划视图回写失败只能触发关联修复或证据缺失提示，不能触发订单重发。

## 4. 工具与交互契约

### 4.1 计划工具

| 工具 | 用途 |
| --- | --- |
| `list_plans` | 当前作用域的有界计划摘要 |
| `read_plan` | 按 ID 读取计划、版本、笔记和证据引用 |
| `create_plan` | 创建结构化草稿 |
| `revise_plan` | 基于指定版本提出修改 |
| `append_plan_note` | 追加有来源的研究说明 |
| `get_plan_review` | 返回由代码生成的复盘事实 |

工具使用明确 schema，不提供静默覆盖式 `upsert`。程序填写作用域、事实来源和执行关联等受信字段，不能由模型自行声明。

尚未实现的工具不得提前注册，也不得用空对象或成功形状的占位结果充数。D2 交付计划管理工具；`get_plan_review` 在 D6 完成后接入。

### 4.2 用户命令

```text
/plan
/plan show <id>
/plan track <id>
/plan archive <id>
/plan review <id>
/plan export <id>
```

归档或删除不取消交易所订单。有挂单或未决执行时必须明确展示，避免用户误以为风险消失。

删除要求用户确认，只删除计划资料，不删除风控或执行事实。导出应排除凭证，并提示计划和账户资料的敏感性；模型不获得任意文件输出权限。

命令输出、确认、错误和帮助均接入现有中英文文案及补全机制。

### 4.3 每轮短索引

复用会话 `before_agent_start` 与上下文消息能力，根据当前账户重新生成索引，包含活跃计划 ID、版本、标的、更新时间和待关注事项。

详细正文按 ID 获取，不全量注入历史。笔记通过非权威上下文提供，不拼进系统规则。索引必须标明过期或尚未刷新，而不是将缓存表述为实时账户状态。

新会话、恢复和对话压缩后，都应从计划存储重建上下文。读取失败必须提示“计划上下文不可用”，不能当作零计划处理。

### D0：版本与首用基线

目标：让用户拿到的发布版本、文档和首次体验一致。

交付：

- 核对当前源码、已发布包与 `[Unreleased]` 的能力差异，修正文档口径。
- 提供一个无需交易所密钥的模拟盘首次体验，标明模型认证仍有独立要求。
- 准备目标用户试用说明和手工记录表，招募由维护者安排。
- 梳理既有独立安装、恢复演练、七天 Paper 长跑和发布证据缺口。

验收：

- 文档不把未发布功能写成已发布能力。
- 首次体验不要求实盘权限，不默默切换到 live。
- 证据状态真实，未完成项目明确保留为未完成。

边界：不得擅自构建、发布、使用付费模型或运行实盘。打包安装和长跑按仓库规则及维护者授权执行。

基线长跑可以提前开展，但最终候选代码变化后必须重新满足 revision 绑定的发布证据要求，不能用旧版本的长跑冒充新版本完成。

### D1：计划模型和存储

目标：先实现没有模型和网络也能工作的计划领域模块。

交付：

- `TradePlan` schema、版本及生命周期契约。
- 独立文件存储、锁、同步落盘、作用域和版本冲突处理。
- 活跃计划及历史资料容量限制。
- Paper 重置后的计划暂停与重新确认规则。
- 内存存储或可注入存储接口，供后续离线用例复用。

验收：

- 保存后重启可以准确恢复；坏文件和未知格式不会变成空数据。
- 两个进程修改同一版本时只有一个成功，另一个收到明确冲突。
- 不同账户和 paper/live 互相隔离，相同账户不因 cwd 不同而隔离。
- Paper 重置不将旧计划和旧执行结果带入新模拟账户。
- 写入失败不报告成功，容量超限不删除旧记录。

非目标：不接下单、不接监控、不引入数据库、不修改风险账本存储模型。

### D2：工具与 `/plan`

目标：用户可以创建、查看、修改和管理计划。

交付：

- 五个计划管理工具及对应 schema。
- `/plan` 列表、详情、跟踪启用、归档、导出及明确的删除入口。
- 草稿与已启用版本的权限区分。
- 双语文案、工具目录、提示词规则和 slash 补全。

验收：

- 用户能够通过一次模拟分析保存计划，退出后仍可查看。
- 模型可改草稿，但不能无提示替换正在跟踪的条件。
- 计划启用确认与订单授权清晰区分。
- 修改计划、启用跟踪和归档不会调用下单或撤单接口。
- 不向模型暴露文件路径、凭证、风控配置写入口。

非目标：不注册未完成的复盘工具，不添加第二套订单执行工具。

### D3：跨会话恢复

目标：计划上下文从独立存储恢复，不依赖聊天记录碰巧仍在窗口中。

交付：

- 每轮当前作用域短索引及正文按需读取。
- 新会话、恢复、压缩和账户切换的生命周期接线。
- 索引容量、过期标记、读取错误与健康提示。

验收：

- 新会话和压缩后都能定位原计划。
- 切换账户后不继续注入旧账户计划。
- 4 KiB 索引限制按 UTF-8 字节实施；超限显示省略提示和查询入口。
- 读取失败明确报告，不返回“没有计划”。
- 笔记中的命令式文本不会改变系统规则、工具权限或交易授权。

边界：使用当前已发布依赖实际提供的 API；不能只凭 workspace 中新增的私有 API 判断独立安装可用。

### D4：只读条件跟踪

目标：让计划在后续使用中持续产生价值，而不是增加自动交易路径。

第一版支持：价格阈值或区间、已收盘 K 线价格条件、计划到期、关联订单变化、保护单覆盖不足。订单关联类能力在 D5 可用后接通；不得先猜测关联。

交付：

- 复用 `ti-triggers` 的确定性条件模型和三态求值。
- 复用监控周期，按标的与周期去重取数，不为每个计划创建独立轮询器。
- 计划条件变化事件、冷却、稳定事件 ID 和健康状态。
- 跟踪停止、版本更新及重启基线的行为。

验收：

- 新增计划提醒在 Paper/live 中都只通知，不自动启动交易回合。
- 不调用下单、撤单或账户设置接口。
- 数据缺失、过期、未来时间戳按未知处理，不等同条件不成立。
- 重启不补算停机期间未观察到的跨越，不把恢复通知当作新信号。
- 重复通知可按事件 ID 识别，不宣称严格只投递一次。
- 已归档或旧版本计划不继续产生现行提醒。

边界：保留原有订单监控和仓位守护的唤醒策略，不因新增计划通知而改变它们。第一版跟随交互进程运行，不实现独立守护服务。

### D5：可靠执行关联

目标：将计划版本关联到现有执行流程，而不重写交易引擎。

实施前必须完成一份简短设计说明，明确提交意图 ID、引擎引用字段、重复请求语义、两个存储的写入顺序、归档确认和容量处理。说明可以放在任务交付描述中，不必另建文档。

交付：

- 不可变的计划版本与提交意图快照。
- 引擎中有界通用引用，随执行记录和风险占用一起持久化。
- 现有 `check_order`、普通订单、OCO 和结果展示的接线。
- 稳定提交意图的去重规则与原始作用域校验。
- 从执行记录修复计划关联的只读流程。
- 提供 D6 所需的证据归档契约和保留边界。

验收：

- 提交前退出时，明确区分尚未提交和结果未知。
- 交易所接受后退出，重启仍能找到原始计划版本与执行记录。
- 相同提交意图在两个进程或重启后重复调用，不造成第二次提交。
- 计划视图回写失败、暂时查无订单或部分 OCO 证据，不触发重发。
- 计划、数量、价格或作用域变化后不复用旧预检和旧执行对象。
- 现有暂停、额度限制、确认、未知结果阻断和恢复行为不被绕过。

非目标：计划不成为新的交易授权系统，不增加自主执行。D5 的局部模拟结果不能独立证明长期复盘或实盘试点就绪；完整发布还依赖 D6 和 D7。

### D6：证据归档与复盘

目标：先由代码构造事实，再由模型解释，避免事后编造理由。

交付：

- 计划版本、数据观测、用户修改、订单与成交的证据时间线。
- 可靠归档及与引擎保留策略衔接的确认机制。
- 原计划与实际订单的差异。
- 在数据完整时计算结果，数据不足时明确缺口。
- `get_plan_review`、`/plan review` 和 TUI 展示。

验收：

- 每个关键结论可以定位到当时版本和证据。
- 不用当前行情或后来获得的信息补写过去的交易依据。
- 未知费用不当成零，未成交订单不计为完成交易。
- 同标的多计划、外部交易和资金变化不被错误归因。
- 日志超过原有终态保留数量后，已归档计划证据仍可读取。
- 归档失败或证据缺失可见，不生成完整收益结论。
- 复盘重复读取不更改交易状态，也不触发新的执行。

非目标：不输出样本不足的策略优劣判断，不宣称统计显著性、盈利提升或完整回测。

### D7：试用与发布收敛

目标：形成一个可独立安装、理解和使用的模拟盘计划工作流。

交付：

- 完整首次体验、计划恢复、跟踪、执行关联和复盘流程。
- 升级、备份、恢复、导出、删除及已知限制说明。
- 与最终候选版本绑定的发布证据。
- 试用问题清单、修正结果和第二阶段投入建议。

验收：

- 用户独立完成保存计划，并在不同日期回来继续使用。
- 独立安装不依赖 workspace 才有的 API 或未打包文件。
- 不跨版本拼接长跑和发布证据。
- 实盘试点未授权时，交付停留在模拟盘和允许的只读范围。
- 所有未满足的门槛明确列出，不用成功占位记录通过发布。

## 7. 开发与验收纪律

实施以根目录 `AGENTS.md` 为准，尤其注意：

- 开始前读取当前 Git 状态和相关文件，不覆盖其他会话修改。
- 修改测试文件后运行对应的定向用例；完成代码变化后执行 `npm run check` 并保留完整输出。
- 不运行 `npm test`、根构建或完整 Vitest 扫描，除非满足仓库规定的明确授权。
- 常规行为用例使用假交易所、固定时间和可注入存储，不依赖真实模型、密钥或付费接口。
- `packages/coding-agent/test/suite/` 如确需涉及，使用既有 harness 和 faux provider。
- 不为通过检查降级现有功能，不添加静默错误兜底，不开放任意文件工具。
- 不擅自提交、发布、安装带生命周期脚本的依赖或操作实盘。

定向 Vitest 的命令形式：

```bash
# 在相应 package 根目录运行，替换为本任务实际涉及的测试路径。
node "$(git rev-parse --show-toplevel)/node_modules/vitest/dist/cli.js" --run src/plans/store.test.ts
```

总体不可妥协条件：

1. 模型声明“已成交”不能改变执行状态，修改计划不能改变风控。
2. 提交意图不会因关联失败或恢复而自动再次提交。
3. 新增计划跟踪不调用下单、撤单或账户设置接口。
4. 复盘事实有来源，缺证据时明确未知。

## 8. 多 Agent 分工与交接

### 8.1 文件所有权

D0 可以与 D1 并行。D3、D4、D5 在 D2 契约稳定后具备逻辑并行条件，但会竞争部分公共文件。

`main.ts`、`context.ts`、`tools/index.ts`、`commands.ts`、`prompt.ts`、`i18n.ts`、包导出和包清单应由明确的一名集成负责人协调。其他 agent 先在独立模块完成工作，再交接公共接线需求。

同一工作区内不得让多个 agent 同时修改同一文件。各任务先确认字段、接口、错误分类和作用域，不得各自实现不同的 PlanStore 或账户身份。

### 8.2 每个任务的交付格式

agent 完成后提交以下信息，而不是只说“已完成”：

| 项目 | 要求 |
| --- | --- |
| 任务 ID | D0–D7 中实际负责的编号 |
| 实现范围 | 完成了哪些行为，明确哪些不在本任务内 |
| 文件清单 | 本会话实际修改或新增的路径 |
| 接口与存储变化 | 新字段、格式版本、迁移或升级限制 |
| 验收证据 | 对应条件、定向命令及实际结果 |
| 未完成事项 | 阻塞、未验证边界和待集成项 |
| 后续依赖 | 下一个 agent 可以使用的接口与仍需等待的条件 |

未实现的 API、未运行的长跑和未授权的实盘试点不得标为完成。

### 8.3 分配任务时可直接使用的指令模板

```text
请执行 docs/trade-plan-agent-development-plan.md 中的 D<n>。

先读取根目录 AGENTS.md、本文的范围/核心决策/验收纪律，以及该任务的依赖交付。
本任务只负责：<模块和明确路径>。
公共文件集成负责人：<负责人或串行集成说明>。

重新核对当前源码，不把调研基线当成当前事实。
先确认依赖接口和作用域；未就绪时报告具体阻塞，不自行发明第二套契约。
保留其他 agent 的改动，不修改分配范围之外的功能。
按本文验收条件完成实现与定向用例，并运行仓库要求的检查。
不提交、不发布、不操作实盘、不调用付费模型，除非维护者另行明确授权。
完成后按本文“每个任务的交付格式”报告。
```

本模板供维护者分配任务，文档本身不启动任何 agent。

## 9. 第二阶段的投入门槛

核心工作流之后，再根据用户反馈选择投入方向，不同时全面铺开。

| 用户主要反馈 | 优先方向 | 边界 |
| --- | --- | --- |
| 不会控制仓位 | 现货计划风险估算、用户设定的单计划上限 | 模型只能提出数量，不能修改上限；止损不保证实际亏损上限 |
| 看不清、找不到 | TUI 列表、详情、时间线、图表标注 | 必要时增加本地只读面板，不直接建设完整 Web 平台 |
| 需要比较历史表现 | 与成熟评估能力衔接 | 明确费用、滑点、数据范围及前视偏差，不将规则回放称为完整回测 |

整账户日内亏损熔断单独立项。它依赖权益、入金出金、外部交易及费用口径，不能简单比较两次余额上线。

## 10. 产品交付与发布门槛

从 D2 开始让目标用户试用，第一轮以模拟盘为主。用户招募和付费安排由维护者负责，不要求开发 agent 擅自执行。

重点记录：首次保存计划耗时、是否跨日期主动回来、复盘是否减少翻聊天和查订单的操作。

建议早期投入门槛：12 名目标用户试用四周，至少一半在第四周仍每周使用两次，至少 3 人为明确的持续价值实际付款。这是小样本产品决策依据，不是行业标准或市场成功证明。

发布仍遵循：

- [已有产品可靠性计划](product-readiness-plan.md)。
- [发布证据要求](trading-release-evidence.md)。
- [交易运维手册](trading-operations.md)。
- [长程记忆设计参考](research/agent-memory-patterns.md)。

第一批交付以 D0、D1、D2 为限，先获得“能可靠保存、查看和管理计划”的用户反馈。没有出现跨天复用前，不启动风险预算扩展或 Web 界面工程。
